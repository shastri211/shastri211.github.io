<Section id="context" title="Context">

A company that opens a role to applicants can receive hundreds of resumes. Hiring Automation is a multi-tenant web application for that situation. Companies sign up, post jobs, and bring in resumes by bulk upload (PDF, DOCX or ZIP) or through a public apply link. The application profiles and ranks the resumes against each job, asks an LLM to evaluate the best matches, and can send shortlisted candidates an email and a browser-based voice interview.

Two parts of that work are slow and fail in ordinary ways: reading and embedding hundreds of files, and calling LLM providers that rate-limit. A hiring tool also holds personal data for many companies at once. Most of the engineering here is about those three facts rather than about prompts.

</Section>

<Section id="objective" title="Objective">

The system is built around four requirements.

- A batch survives a worker crash. No resume is lost, and no resume is processed by two workers at once.
- A company can read and write only its own data, and tests check that instead of convention.
- Model spend and rate-limit exposure grow with the size of the shortlist, not with the number of resumes.
- A provider outage or a malformed model response degrades the result instead of stopping the batch.

</Section>

<Section id="approach" title="Approach">

Resume processing and screening are separate steps. Processing happens once per resume, in a background worker. Screening happens on demand, per job, and reads the stored profiles and vectors.

Before any resume arrives, an LLM turns the job description into a structured profile, and the company's own keep-range and gap threshold are loaded for the gate.

<Section id="architecture" title="Architecture">

Three processes run from one repository: a FastAPI service, a queue worker (`python -m app.worker`) and a React frontend. In the container profile, a migration step runs first and nginx serves the frontend and proxies `/api`, so the API is not exposed directly.

PostgreSQL is the system of record. Redis holds the job stream. Qdrant Cloud holds one collection per embedding model. Routes in `backend/app/api/` are thin, and the pipeline, screening, identity, email, interview and tenancy logic lives in `backend/app/services/`.

The frontend is 30 page modules in React 19 and TypeScript, using TanStack Query for server state and Tailwind CSS 4 for styling.

</Section>

<Section id="engineering" title="Engineering">

### The queue

Resume processing runs on a Redis Streams consumer group. A message that fails is retried up to three times with a 60 second backoff. A worker sends a heartbeat every 90 seconds for the message it is processing; that re-claims the message onto the same consumer and resets its idle time. Without it, a job that legitimately runs longer than the 300 second idle threshold would look dead, and a second consumer would claim it while the first was still working. The stream is capped at 100,000 entries so acknowledged history cannot grow without bound.

Uploads can also fail between "saved to disk" and "put on the stream". Each resume records when it was enqueued, and a recovery sweep re-queues any that never were.

### The gate

Sending every resume to an LLM costs one call per resume. The gate sorts resumes by semantic score, finds the largest drop between neighbouring scores, and cuts there if the drop is at least the company's threshold. If no drop is large enough, it keeps everything at or above the mean. The cut is then clamped between a minimum and a maximum number of candidates, both set per company.

> Illustration, not real data. With scores of 0.81, 0.79, 0.77, 0.52 and 0.50, the largest drop is after 0.77, so three candidates go to the LLM and two are marked `PRE_SCREENED_OUT`.

The function also guards against a misconfigured threshold. If it is zero or below, every gap ties at zero, no cut index is ever assigned, and the comparison still passes. The code keeps everyone instead of raising an error.

### Provider fallback and embeddings

`generate_with_fallback` walks the configured providers in order. A rate limit or a timeout puts that model on a 60 second cooldown and moves on. A configuration error skips the model without a cooldown. If every model is cooling down, it raises `LLMExhaustionError`, a different type from `InvalidEvaluationResultError`, which signals a malformed model response.

Embeddings have two profiles: Gemini at 768 dimensions as the primary, and a local MiniLM model at 384 dimensions as a fallback. Each profile has its own Qdrant collection, and a job remembers which profile it was embedded with, so vectors from two models are never compared.

### Tenant isolation

`organization_id` is stored only on root tables, and everything else is scoped through the job. A request that names another company's object gets the same 404 as one that names an object that does not exist, so the API does not confirm that an ID is real. The isolation test file discovers every route in the application and fails if an authenticated route is neither covered by a cross-tenant case nor on a short, explicit exemption list. A second test is a static detector that flags new queries on root models that are not scoped.

### Candidate identity

An exact email match links a new resume to an existing candidate automatically. A phone-number match only files a suggestion for a human to review; it never merges on its own. Merges are reversible and logged.

### Voice interviews

Interviews use Dograh's browser widget. The application creates a one-time public link; the widget creates the call itself, so no outbound call is placed. Dograh reports results by webhook. Each interview records which attempt generation it is on, and a webhook from a superseded attempt is ignored. A periodic sweep marks interviews that never started as `NO_SHOW`, and that state is terminal and never retried automatically.

### Also in the code

Sign-in locks out after 5 failures per email or 50 per IP in a 15 minute window. Unknown emails count too, so the lockout does not reveal whether an account exists, and the email is hashed in the Redis key. If Redis is unreachable, sign-in fails open so a broken limiter cannot lock everyone out, while the anonymous signup and apply endpoints fail closed. Zip uploads never call `extractall`, and entries above a 100:1 compression ratio are rejected without being decompressed.

</Section>

<Section id="challenges" title="Challenges">

These are bugs from the commit history, each with its cause and its fix.

<Note label="Queue starvation, 15 Sep 2026 (c79e61d)">

A message in retry backoff stayed in the consumer's pending list, and the consumer read that list first on every call. It never reached new entries, so new work stalled behind one failing message. The fix reads new entries first and the backlog second. A retry path needs its own test for what else is waiting while it retries.

</Note>

<Note label="Tests that passed for the wrong reason, 26 Sep 2026 (1970a3c)">

The context sanitizer read two keys, `required_capabilities` and `preferred_capabilities`, that the job profile schema does not have. The real keys are `required_skills` and `preferred_skills`. As a result, certifications and languages were stripped from the evaluation even when the job description asked for them. The sanitizer's tests used the same non-existent keys, so they passed. The fix changed the fixtures to use the real profile shape and added a regression test.

</Note>

<Note label="Two embeddings for one job, 26 Sep 2026 (1970a3c)">

Re-embedding a job under a new profile encoded the profile as JSON, while first-time processing encoded canonical text. That mixed two representations in one job's vectors. Both paths now call the same function for the embedding input.

</Note>

<Note label="Fallback profiles that could never be chosen, 26 Sep 2026 (1970a3c)">

Two newer embedding profiles shared model names with older ones, and profiles are looked up by model name, so they could never be selected. All they did was make the fallback retry the same failing model twice. The fix removed them and added a test that profile model names are unique.

</Note>

Smaller fixes in the same commit: with no SMTP server configured, simulated emails were recorded as sent and are now recorded as simulated, and `/health` returns 503 when a dependency is down.

</Section>

<Section id="trade-offs" title="Trade-offs">

<Decision
  title="Gate on score gaps instead of a fixed top-N"
  chose="Cut at the largest gap between ranked semantic scores, bounded by a per-company minimum and maximum."
  over="Always sending the top N resumes to the LLM."
  because="A fixed N makes the same number of LLM calls for five strong resumes as for five hundred weak ones. A gap-based cut follows the shape of the scores."
  cost="Gap detection is only as good as the embedding scores. If they are poorly spread, the largest gap can be noise, and the bounds then hide that. The repository has no labelled data to tune the defaults against."
/>

<Decision
  title="Profile locally first, and call an LLM only for weak extractions"
  chose="Deterministic local profiling for every resume, with an LLM as a fallback."
  over="An LLM profile for every resume."
  because="Profiling runs for every uploaded file, so an LLM call there multiplies cost and rate-limit exposure by the number of resumes."
  cost="Local extraction misses unusual layouts, and the definition of weak decides when the system pays for a better answer."
/>

<Decision
  title="Redis Streams for the job queue"
  chose="A Redis Streams consumer group, with my own retry, heartbeat and recovery code."
  over="Polling a table in PostgreSQL, or adding a task framework."
  because="Consumer groups already track delivery and pending entries and offer idle-claim, so the queue needs no service beyond Redis, which the sign-in lockout also uses."
  cost="The retry bookkeeping, the heartbeat and the recovery sweep are application code, and the starvation bug above was in it."
/>

<Decision
  title="Scope tenancy through the job"
  chose="Store organization_id on root tables only and reach everything else through the job."
  over="Putting organization_id on every table."
  because="Fewer columns to keep consistent, and a child row cannot disagree with its parent."
  cost="Every query must go through the job. A missed join is a data leak, which is why the route-coverage test and the static detector exist."
/>

<Decision
  title="Integrate a voice platform instead of building speech"
  chose="Dograh's browser widget, driven by a one-time link and webhooks."
  over="A custom speech-to-text and text-to-speech pipeline."
  because="A conversation engine is a separate problem from the hiring workflow, and Dograh already provides one as an open-source voice-agent platform."
  cost="The conversation itself is configured in Dograh, outside this repository, so I cannot unit-test interview quality."
/>

</Section>

<Section id="reflection" title="Reflection">

If I rebuilt it today:

- **Classify provider errors by type, not by text.** The fallback decides whether an error is transient by checking whether the message contains the characters `50` or `400` (`llm_provider.py`, lines 400 to 404). A message that merely contains those digits would be misclassified. Provider exceptions should carry a status code.
- **Share cooldown state.** Model cooldowns live in an in-process dictionary (`model_registry.py`, lines 30 and 31), so each worker process learns separately that a model is rate-limited. Redis would let them share it.
- **Measure before tuning.** The gate defaults came from judgement. A small labelled set of resumes with human decisions would let me tune the threshold and report precision and recall, which is the number this project most needs.
- **Write the architecture down.** The README explains how to run the project but not why it is shaped this way. This page is the first place that is written.
- **Capture screenshots and a short demo.** None exist yet.

</Section>
